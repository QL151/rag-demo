# 企业知识库智能问答系统（RAG + 混合检索 + 精排 + 成本计量）

一个可以**直接跑起来、可以现场演示**的企业知识库问答系统。不是"能回答"的玩具，而是把
**答得准、答不了会说答不了、跑得起、出问题查得到**这四件事都做完了的那一版。

   上传文档 → （增量）切分 → 向量化入库 → 提问
        → 查询改写 → BM25+向量双路召回 → RRF 融合 → 精排 → 阈值拒答
        → 带引用生成 → 缓存 → token/成本计量 → 全链路 trace

前端是零构建单页（原生 HTML/JS），后端 FastAPI，向量库优先 Chroma。

## 一、先看它比"普通 RAG Demo"多了什么

| 能力 | 具体做了什么 | 为什么必须有 |
| --- | --- | --- |
| **混合检索** | BM25（关键词）+ 向量（语义）双路召回，RRF 融合 | 纯向量检索搞不定错误码 / 型号 / 邮箱这类精确值；纯关键词搞不定同义改写 |
| **精排（rerank）** | 召回 20 条 → cross-encoder 精排取 4 条；服务不可用时**自动降级**为 listwise（用对话模型排序） | 召回和精排是两件事。而且精排服务经常"没开通权限"，不能一挂就整体降级 |
| **阈值拒答** | 检索层就把低置信度候选挡掉，判定"没有依据"时**不调用大模型**直接说没有 | 防幻觉最可靠的一层。prompt 里写"资料里没有就说没有"是最不可靠的那层 |
| **多轮查询改写** | "那学生呢？" → "学生版多少钱？" 再送去检索 | 不改写的话，多轮追问就是拿 5 个字去做向量检索，必然召回垃圾 |
| **增量入库** | 文档指纹没变整篇跳过；变了只重新向量化"文字变了"的片段 | 改一个错别字重跑整份文档的 embedding，又慢又费钱 |
| **答案缓存** | 精确命中 + 语义命中（相似度≥阈值）；知识库一改**整体失效** | 企业知识库里 30~50% 的提问是重复的 |
| **成本计量** | 每次调用的 token、费用、首字延迟、P95 落库，`/api/stats` 可查 | 简历/汇报里的"成本降了 X%"必须有出处 |
| **全链路 trace** | 每阶段的耗时、召回条数、各路分数、改写后的问句、为什么拒答 | 用户说"它答错了"时，能从 trace_id 一路看到底 |
| **部门数据隔离** | 片段带 `dept` / `doc_type`，检索时按条件过滤 | 企业客户的第一句话就是"不同部门看到的不能一样" |
| **精排熔断** | 连续失败 3 次后熔断 5 分钟，不再每次提问都白等一次 403 | Key 没权限时，用户会以为"这系统就是慢" |
| **测试** | 89 条 pytest（零联网、6 秒跑完） | 检索质量出问题**不报错**，只能靠测试守住 |
| **阈值标定** | 用探针问题测出"无关问题最高分"的分布，据此定拒答阈值 | 阈值是分数分布上的一个点，拍脑袋定的值在真实语料上往往形同虚设 |

## 二、一次提问的完整链路（面试就照这个讲）

```
浏览器
  │  POST /api/chat/stream
  ▼
app/main.py ──► app/rag.py（编排）
                  │
   ① 取多轮历史（必须在检索之前 —— 改写要用它）
   ② 问题向量化（这一次向量同时喂给"答案缓存"和"向量检索"，不重复调用）
   ③ 查答案缓存 ──精确命中/语义命中──► 直接返回（0 token，费用 0）
   ④ 未命中 → 查询改写（指代消解）
   ⑤ 混合检索：BM25 路 + 向量路 → RRF 融合 →（可选）cross-encoder 精排
                  │            └─ 不可用时 → listwise 精排（对话模型排序）
   ⑥ 阈值拒答：全都不够相关 → 直接说"资料里没有"，不调用大模型
   ⑦ 拼 Prompt（带编号的【参考资料】+ 最近 N 轮历史）→ 流式生成
   ⑧ 结果写缓存、记 token/成本、写 trace
   ⑨ 返回回答 + 引用（带向量分、精排分、命中通道）
```

模块分工：

```
app/
├── main.py         FastAPI 路由（接口 + 鉴权 + SSE）
├── rag.py          ★ 编排层：入库、改写、缓存、检索、生成、计量、trace
├── retrieval.py    ★ 混合检索：分词 / BM25 / RRF / 精排（cross-encoder + listwise）/ 阈值
├── chunking.py     切分（Markdown 标题优先 + 句子聚合 + 重叠窗口）
├── vectorstore.py  向量库抽象：Chroma 优先，纯 Python 兜底；带 where 过滤与版本号
├── llm.py          模型客户端：客户端复用、token 计量、embedding 指纹、失败不静默降级
├── cache.py        答案缓存（精确 + 语义 + 知识库版本失效）
├── usage.py        用量与成本计量
├── trace.py        请求级 trace（JSONL 落盘 + 内存环形缓冲）

scripts/
├── check_embedding.py       配置自检（向量化 + 两路精排）
├── smoke_test.py            一键自测（入库 + 检索 + 提问）

docs/                        归档的评测报告
```

## 三、快速开始

```bash
cd rag-demo

# 1. 建虚拟环境
python -m venv .venv
.venv\Scripts\activate            # macOS/Linux: source .venv/bin/activate

# 2. 装依赖
pip install -r requirements.txt
pip install chromadb              # 可选，装不上会自动降级到内置向量库

# 3. 配置（先复制一份）
copy .env.example .env            # macOS/Linux: cp .env.example .env

# 4. 自检配置：向量化 + 精排能不能调通
python scripts/check_embedding.py

# 5. 自测：入库示例文档 + 检索 + 提问（不需要浏览器）
python scripts/smoke_test.py

# 6. 启动
uvicorn app.main:app --port 8000
```

打开 <http://127.0.0.1:8000>；接口文档 <http://127.0.0.1:8000/docs>。

> 没填 `LLM_API_KEY` 也能完整跑通"上传 → 检索 → 引用展示"，
> 只是不能生成自然语言回答（会返回检索片段）。
> 没填 Key 时**多轮改写和 listwise 精排会自动跳过**，检索链路依然完整。

**Docker 一键起**：

```bash
copy .env.example .env
docker compose up --build
```

## 五、关键设计取舍（面试就考这些）

**1. 为什么必须做混合检索？**
错误码 `40412`、型号 `X200-PRO`、邮箱这类**精确值**，向量模型会把它们映射到语义空间里
"差不多"的位置，召回的往往是意思相近但答案不对的段落；BM25 只认字面重合，一击必中。
反过来，"专业版多少钱"和"价格套餐"这种同义表达，BM25 一无所获，向量检索才对。
两者互补，所以是两路而非二选一。见 `app/retrieval.py`。

**2. 两路分数为什么不能加权平均？**
余弦相似度是 0~1，BM25 是 0~30 的无界分数，量纲完全不同，
`0.7 * 向量 + 0.3 * BM25` 里的 0.3 是在拍脑袋。RRF（Reciprocal Rank Fusion）
只吃"名次"不吃"分数"：每路第 r 名贡献 `1/(k+r)`，k 取论文经验值 60，天然免去调权重。

**3. 精排为什么值得单独一层？**
向量 / BM25 都是"双塔"式检索，快但粗；rerank 是 cross-encoder，
把 query 和文档拼在一起算，准但慢。所以是"两路各召 20 条 → 融合 → 精排取 4 条"，
而不是直接拿 4 条喂模型。**精排不可用时怎么办**：先试 cross-encoder，
失败则降级到 listwise（把候选编号交给对话模型排序）。
但 listwise 给的是**顺序不是分数**，所以拒答阈值仍然用向量分 ——
拿"排第 1 名"去冒充"相关度 0.95"是自欺欺人。

**4. 防幻觉做了几层？**
四层：① 检索层拒答（最可靠，且拒答时不调用大模型，**这次提问成本为 0**）；
② system 提示词强制"资料里没有就说没有"；③ 只把检索到的片段给它；
④ 回答带 `[1][2]` 编号 + 前端展示原文片段与各路分数，人可以直接核对。

**5. 拒答阈值为什么不能拍脑袋？**
先看实测（74 篇 / 1734 段语料，`qwen3.7-text-embedding`）：

| | 最高向量分 |
| --- | --- |
| 无关问题（"怎么养柯基""明天上海下雨吗"等 24 条探针） | 中位数 0.357｜**P90 0.380**｜最大 0.387 |
| 该答对的问题（评测集） | **最小 0.487**｜中位数 0.661 |

结论：**0.25 在这份语料上一个候选都拦不住** —— 上千个片段里总能挑出一个"语义上沾点边"的，
这是极值效应，不是模型不行。所以阈值必须测出来：`python scripts/calibrate_threshold.py`
会用探针问题算出"不该答的问题能拿到的最高分"，据此给出建议值（本语料 → **0.40**）。

更进一步：当"该答对的最低分"和"无关问题的最高分"挨得很近时，调阈值就救不了了 ——
这时该让**精排**来做判断：cross-encoder 直接给相关性分，
listwise 则有一个更强的信号 ——"我把候选都看了一遍，没有一个是相关的"（返回 `[]`）。
这个信号比任何固定阈值都可靠，因为它是读懂问题之后做的判断，而阈值只是分数分布上的一个点。

**6. 多轮对话为什么一定要查询改写？**
不改写的话，检索用的是用户的**原始问句**。用户问"专业版多少钱？"→"那学生呢？"，
第二步就是拿"那学生呢？"这 5 个字去做向量检索，必然召回垃圾。
改写后的问句**只用于检索**，生成侧仍然用原问题 + 历史 ——
否则回答会丢掉用户的原始措辞，历史也会被重复表述一遍。

**7. 缓存最大的坑是什么？**
**知识库一变必须整体失效**。否则用户上传了新文档，提问还是拿到旧答案 ——
这是最难排查的一类线上问题。这里用持久化的 `cache_version` 计数器实现：
任何入库/删除/清空都 +1，缓存键里带上版本号，重启进程也不会漂。
`embedding` 指纹也进缓存键：换了向量模型，旧缓存的语义相似度不再可信。

**8. 为什么 embedding 失败不再自动降级？**
以前接口挂了会悄悄换成本地哈希向量，但**本地哈希和真实 embedding 不在同一个向量空间**，
混进索引后检索会整体错乱，而且不报错。现在直接抛错：
宁可这次上传失败，也不要污染整个知识库。
同时每个片段都记录 embedding 指纹，换模型后 `/api/health` 会明确告警。

**9. 增量入库怎么判断"哪些片段变了"？**
文档级：正文 sha256 写进文档台账，没变整篇跳过（0 次 embedding 调用）。
片段级：每个片段的文本指纹写进向量 metadata，重传时按指纹复用旧向量，
只对真正变了的片段调 embedding。一份 500 段的制度手册改一个词，
从"500 次调用"变成"1 次调用"。

**10. 为什么要 trace，不用现成的 Langfuse？**
现成方案更好，但要额外部署一个服务 + 一个库。小厂第一阶段是"先能定位问题"，
一个 JSONL 文件 + 一个查询接口就够，还能直接 `jq` / `grep` 捞。
真需要看板时，把 `Tracer._write()` 换成 Langfuse SDK 调用即可，上层不用改。

**11. 为什么会话历史 / 计量 / 缓存都用 SQLite？**
练手与内网单机部署优先"零外部依赖"，SQLite 开了 WAL 之后读写不互相阻塞，
支撑单机几十 QPS 没问题；表结构刻意写成与 MySQL 兼容，换存储只需替换一层。

## 六、评测：这些数字是怎么来的

```bash
# 检索策略消融：纯向量 → +BM25/RRF → +精排（同一批向量，只向量化一次）
python scripts/evaluate_retrieval.py "D:\你的\文档目录"

# 便宜试跑
python scripts/evaluate_retrieval.py "D:\你的\文档目录" --limit 8 --sample 20

# 顺便把 4 种切分策略也比一遍（embedding 调用量 ×4）
python scripts/evaluate_retrieval.py "D:\你的\文档目录" --grid

# 小规模命中率检查（评测集在 data/sample/评测集.md）
python scripts/evaluate.py

# 标定拒答阈值：用探针问题算出"不该答的问题最高能拿多少分"
python scripts/calibrate_threshold.py
```

评测集自动生成，两类问题：

- **文档级**：用文档标题提问 → 看能否命中正确的那篇文章（容易，区分度低，只作参考）；
- **章节级**：用 `##` 小节标题提问 → 看命中片段里是否包含该小节（难，区分度高），
  并**剔除"背景 / 总结 / 展望"这类每篇都有的通用标题** ——
  用"一、背景"去检索，命中哪篇文章的背景都不算错，这种问题会把真实成绩拉低十几个百分点。
  这是评测集设计的常见坑。

### 实测结果（74 篇技术文档 / 64.4 万字 / 2125 个片段，Top-K=4）

| 切分 | 检索策略 | 片段数 | 文档级 Top-1 | 章节级 Top-1（剔通用） | 章节级 Top-4（剔通用） |
| --- | --- | --- | --- | --- | --- |
| Markdown 标题切（超长再按句子） | 纯向量 | 2125 | 100% | **68%** | 95% |
| 同上 | 向量 + BM25（RRF 融合） | 2125 | 100% | **90%** | 100% |
| 同上 | + 精排（listwise） | 2125 | 100% | **95%** | 100% |

读法（也是面试要讲的三句话）：

1. **纯向量的短板就在"章节级"上**：文档级 100% 说明"找对文章"很容易，
   但"定位到对的那一小节"只有 68% —— 这才是 RAG 真正难的地方。
2. **加 BM25 + RRF 直接 +22 个百分点**（68% → 90%）：文档里的标题、专有名词、
   版号、错误码这类**精确字符串**，正是关键词路的主场。
3. **精排再 +5 个百分点**（90% → 95%）：RRF 融合后的 Top-4 里偶尔还混着噪声，
   cross-encoder / listwise 把 query 和文档放一起重新算一遍，能把它挤下去。

> 本次实测时 `gte-rerank-v2` 接口返回 `403 AccessDenied by API-Key restrictions`
> （**Key 没开通该模型权限**，不是代码问题），于是自动降级成了 listwise 精排 ——
> 也就是说上表第三行的 95% 是**用对话模型排序**拿到的。
> 这顺带验证了降级链路：连续 3 次失败后熔断 300 秒，之后每次提问不再白等一次 403。
> 开通 cross-encoder 权限后把 `RERANK_PROVIDER=http` 打开即可对比两种精排的效果。

评测方式与可复现性：

- 三种策略**共用同一批向量**（154 个问题只向量化一次，2125 个片段只向量化一次），
  所以"提升"只可能来自检索策略本身，而不是重跑带来的差异；
- 评测时把拒答阈值置 0，只衡量**排序能力**（拒答是另一条独立逻辑，有单独的测试守着）；
- 报告与逐题明细会落盘到 `data/_eval/`，可以直接拿错题复盘；
  本次的原始报告已归档到 [docs/retrieval-ablation-report.md](docs/retrieval-ablation-report.md)。

## 七、简历里怎么写这个项目

> **企业知识库智能问答系统**（个人项目）｜Python / FastAPI / Chroma / BM25+向量混合检索 / Docker
> · 独立实现文档解析 → Markdown 标题感知分块（重叠窗口）→ 向量化 → **BM25 与向量双路召回 + RRF 融合 + 精排** → 阈值拒答 → 提示词约束 → SSE 流式生成的完整 RAG 链路，回答附 `[1][2]` 引用溯源、向量分与精排分
> · 自建评测体系（74 篇 / 64.4 万字真实语料，2125 个片段）：对比 4 种切分策略的章节级 Top-1，
>   并剔除"背景/总结"类无区分度问题；**章节级 Top-1 从纯向量的 68% 提升到混合检索的 90%、加精排后 95%**
> · 针对多轮对话的指代问题引入查询改写（"那学生呢？"→ 完整问句）；基于精排分数做置信度阈值拒答，知识库外问题不编造且**不产生 token 费用**
> · 接入 token 计量与两级答案缓存（精确 + 语义）：实测同一问题从 **3.46s / 0.0035 元**
>   降到 **0.21s / 0 元**（缓存命中时费用恒为 0）；成本、P95 延迟、缓存命中率在 `/api/stats` 实时可查
> · 写了拒答阈值标定脚本：用 24 条探针问题测出"无关问题最高分 P90 = 0.38"，
>   对照"该答对问题的最低分 0.49"，把阈值从拍脑袋的 0.25 定到实测的 0.40；
>   当两者接近时改由精排判断（cross-encoder 分数，或 listwise 的"全部无关"信号）
> · 向量库抽象为统一接口（Chroma / 纯 Python 双实现自动降级）；精排不可用时自动降级为 listwise 排序并**熔断 300s**；
>   文档指纹 + 片段指纹实现增量入库（改一处文字只重新向量化变化的那几段）
> · 89 条 pytest（全部离线、6 秒跑完）+ `/api/stats`、`/api/traces` 观测接口，Docker Compose 一键部署

**注意**：上面每个数字都要能说清出处（第六节的脚本就是用来产出这些数字的）。
特别是 68% → 90% → 95% 这一组：面试官一定会问"你怎么测的"，
答案就是"用 74 篇文档的 `##` 小节标题当问题、剔除通用标题、三种策略共用同一批向量"。

## 八、常见问题

**Q：`pip install chromadb` 失败？** 会自动降级到内置纯 Python 向量库，功能完全一致。
想看当前用的是哪个：看页面顶部状态栏，或访问 `/api/health` 的 `vector_backend`。

**Q：检索效果不好，先查哪里？**
① `/api/health` 看告警（向量模型是否和索引一致）；② `GET /api/traces` 看某次提问的
"召回了几条 / 各路分数多少 / 是不是被阈值挡掉了"；③ `python scripts/evaluate.py`
看命中通道 —— 只出现在"关键词"列说明向量模型对这个表述不敏感。

**Q：为什么提问时提示"精排不可用"？**
`/api/health` 的 `retrieval.rerank_ready` 与 `rerank_llm_ready` 分别对应两种精排实现。
`403 AccessDenied by API-Key restrictions` 表示**这个 Key 没有开通该模型的权限**，
去服务商控制台给 Key 加权限，或把 `RERANK_PROVIDER` 设为 `llm` 只用 listwise。

**Q：上传 PDF 没内容？** 扫描版 PDF 是图片，需要 OCR，本项目不做。换成文字版或 txt/md。

**Q：`.env` 会不会被提交上去？** `.gitignore` 已忽略。提交前务必 `git status` 确认一次。

**Q：`代码逐行讲解与实验手册.md` / `项目讲解与学习路线.md` 还准吗？**
这两份教程写的是 **v0.1 的学习骨架**（切分 / 向量库 / 提示词 / 接口 / 评测那几条主线），
对 `chunking.py`、`vectorstore.py`、`loaders.py`、`main.py` 的讲解仍然有效；
v0.2 新增的 `retrieval.py`、`cache.py`、`usage.py`、`trace.py`、`docstore.py` 请看本 README 与代码注释。

## 九、下一步可以加什么

1. **pgvector / Milvus 后端**：文档涨到十万级时，Chroma 单机持久化会成为瓶颈；
2. **扫描件与表格**：PaddleOCR + 版面分析，企业资料里这类占比很高；
3. **评测自动化**：把 `evaluate_retrieval.py` 挂到 CI 上，Prompt 或模型一改就自动跑回归；
4. **前端工程化**：原生 JS → Vue3/React（很多 JD 要求前端能力）；
5. **鉴权升级**：从单 Key 换成 JWT + 用户级部门权限；
6. **异步化**：SSE 端点当前是同步 `def`（每个流占一个线程池线程），
   高并发下应换成 `httpx.AsyncClient` + `async def`。
